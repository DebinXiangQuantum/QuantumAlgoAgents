# Audit Quantum Advantage

Audit the exact claim the evidence can support. Downgrade wording whenever the evidence
supports only correctness, query complexity, resource projection, or a comparison with a named
baseline.

## Operating Rules

- Respond in the user's language unless the user requests another language.
- Read [claim-ladder.md](references/claim-ladder.md) before classifying a claim.
- Read [benchmark-protocol.md](references/benchmark-protocol.md) before accepting benchmark or scaling evidence.
- Never infer quantum advantage from quantum-circuit execution, simulator performance, fidelity, qubit count, or logical gate count alone.
- Never auto-approve an advantage claim generated by another skill or agent.
- Label each material statement as `source_supported`, `model_inference`, or `uncertain`.
- Attach a primary paper or official project URL to every `source_supported` statement.
- Treat a missing best classical baseline as a limitation, not as evidence that no such baseline exists.

## Audit Workflow

1. Freeze the claim.
   - Quote or restate the smallest falsifiable claim.
   - Record whether it concerns correctness, query complexity, asymptotic runtime, logical resources, physical resources, wall clock, cost, energy, solution quality, or scientific utility.
   - Split compound claims into independently auditable claims.

2. Normalize the comparison contract.
   - Match the problem family, instance distribution, size, input access, output, accuracy, confidence, and success probability.
   - Reject comparisons that ask one method for a full object and the other for a sample, expectation, or certificate.
   - Give classical baselines comparable preprocessing and data-access capabilities.

3. Classify the evidence.
   - Separate theorem, formal proof, simulator result, hardware result, logical-resource estimate, physical-resource projection, and extrapolation.
   - Assign source fitness and one provenance label to every supporting statement.
   - Mark inaccessible, conflicting, or unverified evidence `uncertain`.

4. Place the claim on the ladder.
   - Choose the highest rung whose complete requirements are satisfied.
   - Keep `provable_speedup` as a separate theorem flag; do not infer it from measurements.
   - State every condition that prevents promotion to the next rung.

5. Audit theoretical costs.
   - Expand state preparation, QRAM, sparse access, oracles, block encodings, normalization, condition number, precision, success amplification, output extraction, and verification.
   - Distinguish query complexity from executable gate complexity.
   - Search for quantum-inspired or structure-aware classical algorithms under comparable access.

6. Audit measured or projected costs.
   - Include preprocessing, compilation, mapping or embedding, reset, shots, readout, communication, optimization, mitigation, cutting reconstruction, decoding, and verification.
   - Require a fault-tolerant projection for deep coherent algorithms and inspect sensitivity to hardware and error assumptions.
   - Report queue delay separately from algorithmic runtime and include it in user-observed service latency.

7. Audit fairness and statistics.
   - Require equally serious formulation and tuning for quantum and classical methods.
   - Inspect held-out instances, failed runs, restarts, target quality, confidence intervals, tail behavior, and scaling fits.
   - Reject a crossover or exponent claim that is driven by startup effects, a fixed suboptimal parameter, or too few post-crossover sizes.

8. Issue the verdict.
   - Use `supported`, `conditionally_supported`, `unsupported`, `contradicted`, or `uncertain`.
   - Pair the verdict with the permitted claim wording and ladder rung.
   - Give the minimum additional evidence needed for promotion.
   - Preserve negative findings and counterexamples; do not soften them into advantage language.

## Output Contract

Return these sections in order:

1. `Frozen claim`
2. `Matched comparison contract`
3. `Claim ladder classification`
4. `Evidence matrix`
5. `Hidden-cost and assumption audit`
6. `Classical baseline audit`
7. `Benchmark and statistics audit`
8. `Verdict and permitted wording`
9. `Promotion requirements`

Use this row schema in the evidence matrix:

```yaml
claim_id: string
statement: string
evidence_type: theorem|formal_proof|simulator|hardware|logical_estimate|physical_projection|extrapolation
source_url: string|null
source_fitness: A|B|C|unrated
provenance_status: source_supported|model_inference|uncertain
ladder_rung: C0|C1|C2|C3|C4|C5|C6|none
verdict: supported|conditionally_supported|unsupported|contradicted|uncertain
conditions: []
permitted_wording: string
```
